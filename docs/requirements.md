# Требования Monitoring Core

## Назначение

Мониторинг Windows-компьютеров интерактивной экспозиции внутри LAN. Один локальный
сервер, до 100 устройств. Интернет не требуется после установки компонентов.
Этот инкремент — проверяемый прототип, а не завершённый промышленный релиз.

## Текущий инкремент

| Требование | Реализация / критерий |
|---|---|
| Агент подключается исходящим HTTPS | Никаких входящих портов на ПК; TLS с проверкой CA и имени |
| Heartbeat | Каждые 10 секунд при доступном сервере; 5 секунд timeout; backoff 10/20/40/60 секунд + jitter при ошибках |
| Метрики | Системный CPU, RAM total/available, фиксированные диски total/free, системный uptime |
| Windows CPU | GetSystemTimes с дельтой; первый sample null |
| Идентификация | Заранее созданный UUID, индивидуальный случайный токен 256 бит |
| Статус | Online до 35 секунд включительно; Offline после 35 секунд без heartbeat |
| Отображение | Защищённая Blazor-страница; обновление раз в 5 секунд через Interactive Server / SignalR |
| Хранение | Последний принятый snapshot каждого виденного устройства; PostgreSQL/EF Core |
| macOS | Явный `--simulate`; синтетические данные и маркировка в UI; опциональное volatile InMemory-хранилище |
| Защита | Отдельные agent/operator policies, CSRF для login/logout, secure HttpOnly cookie, rate limit, body limit 64 KiB |
| Проверки | xUnit: validation, auth, Offline, конкуренция, transport, EF model/migration |

Список содержит устройства, отправившие хотя бы один heartbeat. Provisioned, но никогда
не подключавшиеся агенты пока не отображаются. Offline не означает, что ПК выключен:
возможна потеря сети, остановка службы или недоступность сервера.

## Нефункциональные требования

- Плановая нагрузка: 100 / 10 = 10 heartbeat/секунду. Нужен отдельный нагрузочный прогон до промышленного внедрения.
- Не более 32 локальных дисков в payload, проверка диапазонов и предельной длины строк.
- Общая синхронизация времени (NTP); допустимое отклонение SampledAtUtc — 5 минут.
- Секреты не входят в исходники/логи/DTO. Сервер не доверяет DeviceId без привязки токена.
- Production запускается только с PostgreSQL, явными credentials и TLS. Сбой БД не включает dev-хранилище.
- Серверная ошибка не останавливает worker; отмена службы корректно прерывает ожидание и запрос.
- БД и приложение имеют отдельные учётные данные/права; миграции выполняются отдельной maintenance-командой.

## Следующие этапы

История метрик и retention, регистрация/отзыв/ротация credentials, operator identity/RBAC,
наблюдение Unity/Resolume/vvvv, температурные предупреждения, прогноз дисков.
Затем безопасные команды для разрешённых приложений с аудитом. AI-анализ логов — после Monitoring Core.

## Вне текущего объёма

Произвольное удалённое выполнение кода, shell-команды, AI, auto discovery,
централизованный installer/updates, HA, автономная очередь телеметрии, история метрик.
